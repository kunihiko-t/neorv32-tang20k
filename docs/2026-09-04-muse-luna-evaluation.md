# Muse SparkとLunaの実装記録

2026年9月4日に、Muse SparkへUART受信回路とHDMI用端末バッファの実装を依頼した。
レビューだけを依頼したものではなく、採用した2ファイル229行はMuseの初回実装と修正回答に基づく。
親エージェントが仕様、テスト、パッチ適用、HDMI統合を担当した。

## 今回の比較条件

| 項目 | Lunaの前回作業 | Muse Sparkの今回作業 |
| --- | --- | --- |
| モデル | gpt-5.6-luna、high | muse-spark-1.3-contributor-free、high |
| 実装対象 | MiniOSのRV32用UARTシェル | UART受信と64列30行の端末バッファ |
| 言語と規模 | Rust、3ファイル、108行追加と8行削除 | Verilog、2ファイル、229行 |
| 実行環境 | Codex内蔵サブエージェント、ファイル編集とテスト実行が可能 | OpenCode 1.18.27、添付ファイルからパッチを返答、ツールは無効 |
| 計測時間 | 7分2秒、調査からテストと完了報告まで | 初回回答143.26秒、修正回答9.73秒、合計152.99秒 |
| 計測に含まない作業 | 親による実機転送と統合検証 | 親によるテスト作成、適用、実行、統合、ツール不具合の調査 |

異なる課題と実行環境なので、この時間から「MuseはLunaの何倍速い」とは判断しない。
Museへ渡した仕様は、RAM構成、端末の挙動、モジュールの入出力まで親が決めていた。
一方でLunaは既存のRustコードを調べ、ビルドとテストを自分で実行していた。

## 品質と修正の記録

LunaのUARTシェルは、RV64側を維持したままRV32にhelp、info、echo、編集、入力長制限を追加した。
親の途中レビューでCRLF処理を確認して修正し、完了時にはカーネルのホストテスト186件とRV32/RV64のreleaseビルドが通った。
その後、親がMacと実機間でコマンド、Backspace、長文拒否、CRLFを検証した。
これらの実機確認は今回のHDMI追加前の結果である。

Museの初回実装は、基本シミュレーションを一度で通過した。
UARTの連続フレーム、不正な停止ビット、短い開始パルス、端末初期化、通常の編集、折り返し、スクロールを確認した。
Yosysの単体合成では端末メモリーが1個のDPX9Bに収まった。

ただし、初回には「64文字ちょうど書いた直後のBackspace」でカーソルを1桁余計に戻す不具合があった。
親が追加した再現テストでは、末尾ではなく末尾から2文字目が消え、3つの検査が失敗した。
失敗ログとテストをMuseに返すと、Museは原因を説明して不要な1行を削除するパッチを返した。
修正後はその再現テスト、64文字直後の改行、UARTから端末への接続テストも通った。

HDMIとの統合では、親がRAMとフォントの読み出し遅延に画素と同期信号を合わせた。
Lunaによる独立レビューでも重大な問題は見つからなかった。
2個のPLLを使うと発生したビットストリーム生成ツールの例外は、Museに依頼した端末実装の不具合とは分けて扱う。
この例外はプロセス内の互換補正で解消し、HDMI統合版のビットストリーム生成まで完了した。
CPUの96MHz制約と映像の27MHz制約を満たし、LUT4は29.8%、BSRAMは60.9%だった。
その後、親がSRAMへ転送し、MiniOSの全5,514語の一致とUARTシェルの実機テスト通過を確認した。
最後にユーザーの目視で、モニターに`echo HDMI MIRROR READY`などの出力と最下行の`minios>`が表示されることを確認した。
Museの実装を含む統合版で、UART出力からHDMIへの文字表示まで実機で動作した。

## コストと運用上の評価

OpenCodeが返したMuseの実装2回分のcostは、ともに0だった。
親エージェントの検証と統合、LunaのレビューはCodexの利用量を消費するため、作業全体が無料になったわけではない。
Lunaについては、この実行単位のドル建て料金は取得していない。

後から確認した[OpenAIのLuna標準API料金](https://developers.openai.com/api/docs/models/gpt-5.6-luna)は、100万トークンあたり入力$0.20、キャッシュ入力$0.02、出力$1.20だった。
前回のLuna実装ログをこの料金へ換算すると、キャッシュを除いた入力92,418、キャッシュ入力2,330,112、出力14,084から約$0.082となる。
これはAPI換算の試算であり、Codexの実際の請求額やサブスクリプション枠の換算ではない。
親エージェントの処理と別のレビューも含まない。

[Meta公式のMuse Code料金表](https://developer.meta.com/ai/products/muse-code/)ではHigh Usageは月$15、Everyday Usageの3倍の利用枠と案内されていた。
無制限ではなく、この月額契約がOpenCodeの今回の呼び出しに適用できるかは未確認である。
Lunaの前回作業と同じ消費量なら100件で約$8.20、200件で約$16.40となるが、Muse側の課題あたり消費枠が未測定なので損益分岐点の実証にはならない。
ユーザーの選択により、今後の小さな実装とレビューはLunaを使う。

Museの最初の接続準備では、CLIの引数解釈とファイル権限設定でそれぞれ失敗した。
これらは実装前の環境設定の失敗として分け、実装の誤答数や上表の時間には含めていない。
権限で止まった際、Museはファイルを読めたふりをせず、未実行であることを報告した。

今回の結果から、仕様とテストが揃った小さな実装や、再現手順のある修正をMuseへ渡す運用は継続できる。
既存リポジトリーの調査からテスト実行まで自走する能力は、このMuse実行では評価していない。
同一課題を同じ初期状態と同じ権限で解かせてはいないので、モデル全般の品質順位はつけない。

Muse Contributor Freeの利用では、送信内容の学習利用について説明し、ユーザーの同意を得てから実行した。
送信したのはこの課題の仕様とHDL、テストだけである。
無料提供や利用条件を次回も同じと仮定せず、継続時は[OpenCodeのプライバシー説明](https://opencode.ai/docs/zen/#privacy)を確認する。
